# 2.5.0 - 2026-08-15

## Added

- `ToastOptions.severity` (`ToastSeverity.INFO`/`SUCCESS`/`WARNING`/`ERROR`) - now the sole driver of a toast's `role`/`aria-live`, fully decoupled from `color`. Previously, `role`/`aria-live` were decided by strict-equality against the bundled `ToastColor.WARNING`/`ERROR` hex constants, so a custom `color` overriding the palette silently lost the assertive announcement for warning/error toasts.
- `severity` also picks `color`'s default from `configure()`'s `colors` palette when `color` itself is unset, so `severity: ToastSeverity.WARNING` alone gets both the right look and the right role. Pass `color` too for a custom look with the same semantics.
- `ToastsConfig.colors` for reconfiguring the severity -> default color palette library-wide, and `ToastsConfig.severity` as the library-wide default severity for calls that omit it.
- `ToastBuilder.withSeverity()`; `asInfo()`/`asSuccess()`/`asWarning()`/`asError()` now set `severity` (not just `color`), so they stay meaningful under the new model.
- New public exports: `ToastSeverity`, `ToastSeverityValue`.
- Dependabot configuration for automated weekly dependency updates across npm packages (root and demo) and GitHub Actions.
- `unpkg` CDN cache warm-up step in the release workflow, priming the CDN before a release is announced so the first real user isn't the one eating a cold-cache request.

## Changed

- `ToastsConfig.color` (a flat library-wide default color) is retired in favor of `ToastsConfig.severity` - the default-color knob is `colors[severity]` alone now, so there's one source of truth for what color an unset toast gets.
- `promise()`'s `success`/`error`/`timeout` outcomes now carry both `severity` and `color`.
- Codecov action upgraded to v7 (from v5).
